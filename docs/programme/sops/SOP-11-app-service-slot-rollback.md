# SOP-11 — App Service Slot Rollback

Execution status: **REPOSITORY_EXECUTABLE_STAGING_REHEARSAL_REQUIRED**

## Owner
Application Platform Owner

## Purpose
Return an unhealthy managed application release to the last accepted immutable App Service package or slot state without implicitly rolling data backward or bypassing owner-controlled traffic changes.

## Trigger
Failed health, security, role/isolation, performance or runtime acceptance after a managed-staging deployment, production-candidate deployment or owner-approved App Service slot promotion.

## Prerequisites
1. Exact current and last accepted application SHA/package digest for the affected application.
2. Current App Service app/slot identity and traffic state recorded from authoritative Azure evidence.
3. Database migration version and compatibility state known.
4. Incident/change record with rollback owner and approval appropriate to the affected environment.
5. For production traffic changes, explicit owner authority for the affected slot/hostname boundary.

## Permissions
- App Service deployment/slot authority scoped to the affected application and environment.
- Database mutation or restore permission is excluded unless SOP-12 or SOP-08 is separately invoked.
- DNS/Front Door/custom-domain authority is excluded; invoke SOP-40 or SOP-10 when that boundary must change.

## Steps
1. Freeze further deployments to the affected application and record the current SHA, package digest, app/slot name, health state and database migration version.
2. Classify the rollback boundary before changing anything:
   - **managed staging:** redeploy the last accepted immutable staging SHA/package to the same governed staging app only after confirming schema compatibility;
   - **production candidate before promotion:** do not swap or bind traffic; preserve the failed candidate as evidence and redeploy/replace only the candidate slot;
   - **production after an owner-approved slot promotion:** verify the previous production package remains available in the reciprocal slot and that slot configuration/secret references are correct before considering a reverse slot swap.
3. Determine whether the failure is code/configuration-only or coupled to a database migration. If data compatibility is unknown, **STOP** and invoke SOP-12; never infer that an application rollback makes data safe.
4. For a code/configuration-only rollback, verify the last accepted package digest and environment-specific settings/Key Vault references before deployment or slot action.
5. If reversing a production slot promotion, change only the affected application boundary and only with the recorded owner approval. Do not change DNS, certificates, unrelated Front Door routes or another application in the same action.
6. Run the governed health, authentication/authorization, customer-isolation, form/upload, private-storage, integration and monitoring acceptance appropriate to that application.
7. Reconcile queues/outbox/integration events and any state written during the failed release. A clean application health check does not prove state reconciliation.
8. Preserve the failed SHA/package/slot evidence until incident/change closure; record the final traffic and package state.

## Evidence
- Environment and application; before/after app/slot names; current/prior SHAs and package digests; migration version and compatibility decision; owner approval where traffic changed; health/authn/authz/isolation/private-storage/integration/monitoring results; state reconciliation; start/end timestamps; operator.

## Stop Conditions
- Prior package/slot is unavailable or its digest cannot be verified; app/slot identity is ambiguous; schema compatibility is unknown; required Key Vault/configuration references differ unexpectedly; rollback would reintroduce a known security flaw; customer isolation fails; production traffic change lacks owner approval.

A STOP condition keeps production on the safest accepted boundary or the existing public fallback and blocks further promotion until the recovery path is proven.

## Escalation
- Release Owner, Application Platform Owner, Database Owner and Security Lead; Domain/Edge Owner if Front Door, custom-domain or DNS state is implicated.

## Rollback
- Before production promotion, rollback means replacing only the failed candidate/staging package with the last accepted immutable package. After an owner-approved production slot promotion, a reverse slot action is permitted only when the prior slot and schema/configuration compatibility have been verified. Never automatically reverse database state.

## Recovery
- Implement a reviewed forward fix, reconcile state generated by the failed release, repeat managed acceptance, and retain rollback evidence. If the incident exposed a backup/data-recovery weakness, invoke SOP-07 and SOP-08 before resuming stateful promotion.

## Review Cadence
- Rehearse in managed staging before R3, after App Service/slot topology changes and before first production cutover acceptance.

# Master Specification Conflict Register

Status: active
Last reviewed: 30 July 2026

This register resolves duplicated, conflicting or unsafe requirements in favour of security, regulatory accuracy, accessibility, performance and maintainability. A resolution does not convert an external or evidential dependency into a completed feature.

| ID | Conflict or ambiguity | Evidence/current condition | Resolution | Validation or gate |
|---|---|---|---|---|
| CR-001 | The specification requires complete working controls, while the current production host is static | Corporate login, contact and account-application interfaces are published but their API returns 404 | `PUBLIC_ONLY` output must omit every server-dependent login, password, upload, account and secure-workflow control. A functional server-backed control is published only in `FULL_PLATFORM` | Artifact-mode tests, dead-control scan and live synthetic checks |
| CR-002 | The specification says implement everything, while Azure, Entra, Graph, SharePoint, email, DNS and legal approvals are external | No production managed runtime or approved credentials are available in repository context | Implement complete contracts and fail-closed states, then retain each external item as `owner-controlled`; never simulate completion | Staging evidence plus explicit owner approval for production |
| CR-003 | The specification prohibits placeholders, while some claims, portraits, licences and relationships lack evidence | NIT legal relationship and several leadership/regulated titles require documentary confirmation | Omit or retain a deliberately neutral evidence-bound state; do not invent content or publish a role solely because the master text names it | Evidence register and owner/legal/regulatory approval |
| CR-004 | Earlier leadership titles differed across public surfaces | Superseded current-title combinations existed for Prabhakar Lahare and Dr Nishita Trivedi | Apply the owner-approved 7 August 2026 canonical titles everywhere; keep founder, statutory-director and regulated-appointment facts in separate governed fields | Resolved at repository level; production verification pending |
| CR-005 | `Responsible Person` is a regulated appointment as well as part of an approved visible title | The owner approved Dr Nishita's combined public title while the formal appointment record remains unavailable in the repository | Publish the exact owner-approved title, model CTO and RP separately, and keep legal entity, authorisation, site, scope and documentary proof as an explicit controlled evidence gate | Public-title consistency complete; formal documentary verification pending |
| CR-006 | One ecosystem can be interpreted as one undifferentiated design | Current properties have distinct purposes and established visual strengths | Share facts, tokens, controls and quality standards while retaining property-specific art direction and journeys | Cross-estate design review and property acceptance |
| CR-007 | SharePoint is described as the document backbone and elsewhere a unified data architecture is required | SharePoint cannot safely replace identity, session, isolation, transaction and audit authority | Use Azure SQL for application/security/transaction authority; use SharePoint for controlled documents and selected Microsoft 365 registers with explicit field authority | Data-boundary tests, sync reconciliation and permissions review |
| CR-008 | Previous instructions require zero out-of-pocket Azure charges while the target production architecture includes paid services | Production App Service, private networking, WAF and other capabilities may incur charges | Preserve paid-production IaC but do not provision paid resources without a new explicit cost approval. Repository implementation may proceed | Azure Cost Management evidence and owner approval |
| CR-009 | The project requests immediate completion while the public sites must not be disrupted | Three live Pages deployments currently carry public traffic | Use a strangler migration, parallel staging, route comparison and reversible DNS cutover. No big-bang replacement | Migration rehearsal, DNS snapshot and rollback drill |
| CR-010 | The project requests history sanitisation without disclosing or repeating the retired credential | Active tracked history scans clean, but GitHub-managed pull refs 1-4 remain and the exact value is unavailable in the protected environment | Keep the credential retired; complete exact-value scan only through a protected local file; use GitHub Support for provider-managed refs. Never request or print the value in chat | Protected all-ref scan and GitHub Support closure |
| CR-011 | Repositories are public, while the master requires an enterprise secure platform | Public source is acceptable only if no secrets, confidential content or private architecture data are present; portal data is never repository content | Keep all runtime secrets/data external; recommend private repositories for secure platform ownership but require owner decision before changing visibility | Secret/data scan and repository settings review |
| CR-012 | The NIT app is already Next.js, but its generated static output is committed and linted as source | Lint reports 2,427 generated-file findings | Separate source from deploy artifact, ignore generated output and publish through a build artifact rather than treating `_next` output as authored source | Clean lint, build and artifact inspection |
| CR-013 | Rich media is requested, while performance and reduced motion are mandatory | Existing visual systems already use entrance motion and large images | Media must have responsive derivatives, intrinsic dimensions, poster/fallback, reduced-motion behaviour and budgets. No motion may carry essential meaning | Browser, reduced-motion, LCP/CLS and asset-budget tests |
| CR-014 | SEO/GEO work requests broad discoverability, while healthcare and portal content require caution | Public corporate content is indexable; secure routes must never be discoverable | One public canonical entity system; noindex plus authentication for portal/admin; crawler policies distinguish search discovery from model training | Crawl, sitemap, robots, auth and rendered-source checks |
| CR-015 | Legal pages are required to be complete, but legal and reporting applicability depends on company facts and professional review | Turnover, operating status, retention decisions and legal approval cannot be inferred | Publish factual, clearly labelled policies; mark solicitor/accountant review and statutory applicability as pending where evidence is absent | Factual data map, owner confirmation and professional review |
| CR-016 | The specification requests real integrations and forbids mock integrations, while staging must use synthetic data | External systems may be unavailable or unsafe to connect during repository work | Contract tests may use deterministic test doubles, but no integration is described as live until a real isolated environment is verified. | CR-017 | An administrator is asked to have all scopes, while least privilege is also required | Scope aggregation can overexpose customer or board records | The named administrator may hold all application scopes, but record and document access remains resource-authorised and audited. | CR-018 | Existing strong work must be preserved, while the master calls for replacement of the source architecture | Corporate content/media/tests and founder editorial evidence are valuable; static builders are not the target | Migrate approved content, media and tests into typed packages; retain old builders only until parity/rollback acceptance | Content/route diff and decommission checklist |
| CR-019 | Knowledge Panel and AI visibility are objectives, but they cannot be guaranteed | Search platforms decide presentation and citations | Build consistent entities, sources, schema and crawlability; report eligibility and owner actions without outcome promises | Schema/crawl validation and branded-search monitoring |
| CR-020 | Modern Slavery and environmental pages are required, but statutory applicability is fact-dependent | Current turnover/group/size evidence is not established in repository evidence | Publish voluntary policies unless statutory applicability is verified; do not label them mandatory statements or report unaudited emissions | Annual applicability review and solicitor/accountant confirmation |

## Precedence rule

When a later implementation choice exposes confidential data, invents evidence, bypasses authorisation, worsens accessibility or creates an unapproved charge, this register and the master integrity rules take precedence over a literal feature request.

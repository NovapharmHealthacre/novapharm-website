# Retail promotions, gift cards and BNPL release contract

Status: draft; no live payment settings, discounts, or gift balances changed.

## Existing integration
The public Nutraxin API prices orders using the server-only owner-approved SSM register, then writes the DynamoDB ledger and calls the private Stripe hosted Checkout worker. Signed webhooks require the exact durable amount. Stripe's planner accepted retention of hosted Checkout. Live Stripe Default configuration showed card, Apple Pay, Link and Klarna available/on; Clearpay, Billie, PayPal and Google Pay unavailable/off. Account-level availability is not proof of SKU eligibility or completed customer payment.

## Promotion phase
The draft public retail API accepts promo_code and derives a discounted net line amount from an explicitly approved SSM retail_promotions campaign. No production campaign is supplied. Campaigns in this first slice are reusable percentage offers; no first-purchase, global usage cap or fixed amount claims. Each has starts_at/ends_at (epoch seconds), approved, revision, discount_bps (1–5000), minimum_gross_minor and sku_min_net_minor (explicit eligible SKU and owner-approved minimum net unit price including all relevant cost assumptions). Amounts are integer pence. Recalculate VAT per unit under existing approved pricing assumptions, persist original and discounted totals, bind code/revision and amounts into the basket hash. Never enable Stripe unrestricted allow_promotion_codes: the ledger requires the exact final charged amount. Gift redemption is explicitly rejected rather than silently charging the full price.
Implemented in draft: read-only /quote preview shares checkout pricing logic, final checkout requires the same quote basket version, and public Bag displays server-verified apply/remove controls only after backend readiness advertises support. Basket changes invalidate the discount. New attempts receiving an explicit pre-payment promo rejection can reapply their code; reused or uncertain attempts remain locked pending reconciliation. Remaining: portal UI, browser acceptance and stale/expired-quote recovery across reloads, consistent order summary/invoice and refund allocation, rate limiting and error UX, admin permissions and audit, customer-identity enforcement for limited promotions, tests with approved cost/fee floors and sandbox E2E. No active public promotion until signed-off pricing and terms.

## BNPL
Existing worker uses dynamic methods. Verify Klarna permission for each eligible product, retail use case and fulfilment terms (manufacturer lead time may be up to 30 days). No B2B or gift-card purchases on Klarna, per https://docs.stripe.com/payments/klarna/compliance. Review account restrictions and exclude ineligible payment methods per session or use dedicated configurations before marketing. Verify successful/failed/expired asynchronous events and refunds; retain cards and Apple Pay. Use Stripe Payment Method Messaging Element and current approved UK credit disclosures, not invented instalment amounts. Do not advertise Clearpay or Billie until available and approved. No production changes implied.

## Gift card phase
Stripe's native gift-card product documentation (https://docs.stripe.com/payments/gift-cards) describes limited preview for US/USD and supported third-party closed-loop providers, not a turnkey UK online store-credit ledger. Confirm Stripe approval for closed-loop gift-card sales and UK voucher tax/accounting treatment before accepting money. Prefer existing DynamoDB payment ledger and transactional writes rather than introducing a second balance authority. Separate purchase Checkout flow from physical merchandise and prohibit BNPL on gift card purchases. Issue a cryptographically random bearer code only after signed paid webhook, store keyed digest not plaintext, deliver via secure email flow; prevent code guessing, replay, excessive balance inquiries. Durable append-only issue/reserve/capture/release/refund/void journal; atomic conditional reservations on balance and order, expire safely only after checking Stripe state, full gift-funded order requires separate atomic settlement with no zero-value Stripe charge. Partial tender is not a promotional discount: reconcile sales, voucher liability, tax, external cash and internal gift redemption independently. Handle payment failure, cancellation, refund, dispute/chargeback, duplicate webhook and concurrent redemption; audit and reconcile daily. Never enable live redemption until those state-machine and accounting tests pass. The draft includes an isolated offline gift-card balance contract and synthetic tests for denomination matching, random code digests, split tender, reservation, capture, release, refund, stale version and unused void. The draft now also contains an unwired DynamoDB adapter with conditional card version writes, unique purchase and order tender markers, and a durable operation journal with exact-request replay and an inspectable audit record. Tests use synthetic storage, including transaction rollback and lost-response replay. No AWS deployment or new infrastructure was performed. The adapter does not authenticate requests or verify provider payment evidence; it must not be exposed until a private authorised orchestration layer atomically reconciles the authoritative order and Stripe cash tender, and handles disputes, code delivery, accounting and operational reconciliation. The private purchase contract now constructs a separately approved, hosted Checkout request only with a dedicated non-default card-only configuration; the default live payment configuration must not be reused for gift cards. It validates mode, purchase and session IDs, currency, amount, payment intent, captured card charge, refund/dispute state and configuration before issuing. A dedicated keyed pseudorandom issuance code can be reconstructed for delivery retries without storing plaintext; persist separate issuance and lookup key versions and enforce restricted KMS/Secrets Manager access. Synthetic tests cover duplicate issuance, non-card and unapproved configurations, and mismatched/refunded/disputed payments. This module makes no provider calls. The private issuance path now supports an atomic delivery outbox containing purchase and key-version references, not email addresses or plaintext gift codes. An unwired delivery worker loads the authorised recipient and independently retrieves payment evidence, validates the reconstructed code digest, conditionally claims the outbox once, and records a send reference or REVIEW on ambiguity. A lost claim or send response must not trigger blind resend. Synthetic tests cover replay, ambiguous sends, disputed payment and incorrect key resolution. Remaining: authenticated immutable purchase persistence, real Stripe retrieval, signed event routing, secure key-version storage, SES or equivalent sender, operational review of CLAIMED/REVIEW states and a durable refund/dispute workflow to prevent further spending; no delivery or payment is enabled. No live gift product or code issued in this draft.

## Private purchase lifecycle
The new sandbox-only PurchaseStore and orchestration candidate persist an immutable authorised subject, encrypted recipient envelope, denomination, configuration and key versions before requesting Checkout. Conditional state transitions bind the provider request fingerprint and session; uncertain opening retries use the same idempotency key and stop after 23 hours for manual reconciliation. Payment completion requires independently retrieved provider objects and an exact durable session match; issuance and delivery are replay-safe if the summary update fails. Synthetic tests cover subject mismatch, duplicate create/open/settle, policy denial and bounded retries. The trusted provider, recipient encryption, authentication, webhook dispatcher and key adapters still need integration; no route or live processing is enabled.

## Customer preview and sandbox provider
The generated `/products/nutraxin/gift-cards/` page is a noindex, nofollow design preview with five selectable denominations, accessible controls and a disabled purchase button. It has no recipient form, checkout request or redemption capability and is not advertised in navigation. The private StripeSandbox adapter rejects live credentials, checks the account, restricts requests to fixed Stripe API endpoints and uses the existing purchase idempotency contract. Synthetic HTTP fixtures verify form encoding, account checks and payment retrieval. No actual sandbox credential or test-mode payment was available in this run. The adapter still requires trusted credential provisioning, approved dedicated configuration and real sandbox integration tests before live enablement.

## Adverse payment safeguards
The isolated ledger now supports a permanent frozen state: new reservations and capture are blocked, prior transaction history is retained, and a verified unpaid reservation may be released without restoring spendability. Stable verified refund approval IDs are unique across gift refund writes. The private sandbox adverse-payment adapter reconciles the original issued purchase, session, intent and charge before freezing on dispute or refund evidence. No automatic unfreeze, cash refund or production payment action is performed. Remaining: authenticated signed-event dispatch, race-safe handling of adverse events before/during issuance, real provider and ledger integration, accounting and operational review of already-captured or disputed balances. Synthetic tests exercise frozen reservations, mismatched evidence and repeated refund approval IDs.
